## 4c. Pending-PNR â†’ order creation (auto-invoice parity)

When an IUR arrives **without an M801BILL auto-order command**, `createIUR` creates the services/costs/invoices but leaves them as a **pending PNR** (no `order_id`, passengers `is_processed=false`). An operator later turns it into an order. There are **two distinct backend endpoints** for this, reached from different UI pages â€” both previously created/kept the invoice **row** but never issued the invoice **document**, so auto-invoice customers got no invoice:

```
POST /service/create-from-group-pnr â†’ serviceController.createOrderFromGroupPNR   (IURDetailsByPNR.jsx)
      â†’ COPIES pending services' cost/invoice rows onto NEW services on the order
POST /order/assignServices          â†’ orderController.createOrderWithServices     (Order/IUR.jsx, IURDetails.jsx)
      â†’ REASSIGNS the existing pending services' order_id (reuses their existing invoice/cost rows)
```

**Shared fix:** `services/autoInvoiceDocs.js` â†’ `generateAutoInvoiceForOrder({ orderId, invoices, costs, services, userId, userName, companyCode })`. Both endpoints call it **after their transaction commits** (the PDF generator self-calls the backend over HTTP and must see committed rows). It:

- Reads `customer.auto_invoice` via the order's `customer_id` (`>=1` â†’ generate; `2` â†’ `Printed`, else `Raised`); no-op when Off.
- Auto-fills mandatory customer required-data-field defaults; if a mandatory field has no default, **blocks auto-print** (leaves invoices `Raised`).
- Issues one invoice doc for all invoices (`..IN########`) + one XO per supplier (`..XO########`) via the shared `services/documentNumbering.js` (see Â§5).
- Auto-emails when `auto_invoice = 2` **and** `customer.auto_email` and â‰¥1 contact email and an invoice doc was produced.
- Per-invoice/-cost dedupe guard: skips any invoice/cost that already has a document, so re-runs don't double-issue.

**Pitfall:** there are two endpoints; fixing only one leaves the other broken. The `createOrderWithServices` path is the one most easily missed (it lives in `order.controller.js`, not `service.controller.js`). The sibling `transferServiceToOrder` (`/service/transfer-to-order`) only reassigns `order_id` and does **not** auto-invoice (not wired â€” add `generateAutoInvoiceForOrder` there too if that flow ever needs it).

## 5. Document model + numbering

`power_suite_backend/controllers/document.controller.js`:
- Line ~988: branches rendering on `document_type === "costing"`
- Line ~1286: renders `pages/costDocument.ejs`
- Line ~2064: creates documents with `document_type: "costing"`

Numbering scheme (gapless, per company + branch prefix):
- Invoice: `{branchCode 2-char}IN{8-digit number}`, `document_type: 'invoice'`
- XO/Cost: `{branchCode 2-char}XO{8-digit number}`, `document_type: 'costing'`

**All numbering lives in `power_suite_backend/services/documentNumbering.js`.** Never inline a typeCode, padLength, or gap-fill loop at a call site â€” every path goes through `allocateDocumentNumber()` inside `withDocumentNumberLock()`:

| Call site | Documents |
|---|---|
| `document.controller.js:createDocument` | manual invoice + cost |
| `lccImport.controller.js` | LCC invoice + cost |
| `service.controller.js:createIUR` | IUR invoice + cost |
| `services/autoInvoiceDocs.js` | pending-PNRâ†’order invoice + cost |

Three invariants the old inlined copies each got wrong:

1. **Format.** Cost docs are `XO` + 8 digits. The three automated paths used to emit `X` + 9 digits, creating a *second* sequence restarting at 1 whose rendering is near-indistinguishable (`KHX000000001` vs `KHXO00000001` â€” digit zero vs letter O). ~102 legacy `X`+9 rows remain in the DB and were intentionally **not** renumbered; they are invisible to the `XO` regex, so they neither block nor advance the live sequence.
2. **Scope.** `document_prefix` is *not* globally unique â€” nine branches across seven companies share `KH`. The "which numbers are taken" lookup must be filtered to the current company's branches (`document â†’ service â†’ order`, `branch_id IN (company's branch ids)`). Unscoped, the sequence counts other companies' documents and jumps (observed: company 7012 went `KHIN00000001` â†’ `KHIN00000310`).
3. **Serialization.** Allocation is read-then-write, so it must hold the MySQL named lock `docnum:{company}:{branchCode}:{type}` across allocate *and* insert (and, for `createDocument`, until its transaction commits). Otherwise two concurrent imports read the same "next" number.

Gap-fill semantics: the next number is the lowest positive integer not yet used within (company, branchCode, type) â€” holes left by voided/deleted documents are refilled.

## 9. Common pitfalls / gotchas

- **`bspSupplierId` is required** for normal flows. If the company has no BSP supplier configured, services are created with `supplier_id = null` and XO generation will skip those costs (logged, not failed).
- **Order reuse by PNR** can quietly attach new services to an old order. The `existingOrderId` from the frontend batch takes priority over DB lookup.
- **`transactionType` auto-upgrade A â†’ B**: if file is marked EMD-only but contains real ticket passengers, the controller upgrades to B at ~line 1293. Don't fight this.
- **Invoice and XO share the same `shouldAutoGenerateInvoice` guard.** If you ever want to decouple them, add a separate flag â€” don't repurpose this one.
- **PDF generation is synchronous and hits the backend over HTTP** (`APP_URL`). It can be slow; failures are caught and logged, not fatal.
- **De-duplication**: tickets/EMDs/reissues already present on an order are filtered out before creation. Watch for `existingTicketsInOrder` set logic.
- **Email** only sends when `auto_invoice === 2 (Printed)` AND `auto_email` AND there is at least one customer contact email AND an invoice doc was produced.
- **Tax totals must be scaled by `typeCostInfo.count / passengerCount` after dedup.** `iurParser.js:formatParsedData` builds `costByPassengerType[paxType]` from M2 fares AND from an M5 supplement loop that adds entries for header passengers without an M2 record in this file (re-ticketing IURs and batched-by-pax IURs both hit this). The supplement bumps `count` and `baseFare` and stacks an `TX` lump tax on top of any M2 detail codes. `createIUR` then dedups passengers already in the order, so `passengerCount` is often smaller than `costByPassengerType[paxType].count`. The controller rescales `baseFare`/`taxes` by `passengerCount / typeCount` before per-passenger math â€” if you ever remove that scale, the imported cost/invoice values double (or worse). Symptom: a service's tax breakdown shows BOTH `TX = N` and detail codes summing to `N`, totalling `2N`.
- **M5 contains history, not just the current ticket.** In re-ticketing IURs (M01 issued after a void), the file lists multiple M5 rows for the same passenger â€” both the already-voided historical ticket AND the new one. The M2 fare record carries the ticket *actually being issued in this file*. The parser (`iurParser.js:formatParsedData`) prefers an M5 row whose `ticketNumber` matches the M2 fare's `ticketNo` before falling back to the older "first M5 wins" heuristic. If you ever loosen this rule, expect over-voidation: the de-dup logic in `createIUR` will silently skip new tickets because they look like historical ones already in the order. Symptom: "X tickets should be active but only Y are."

- **One passenger can hold multiple separately-issued tickets (split itinerary).** A single M1 passenger with no M2 fare can have several M5 ticket rows â€” e.g. an invoice-only (Type 2) IUR where one direction is ticketed on PD and the return on UA, each its own validating carrier and ticket number (real case: `SJPMâ€¦587`, PD `7416202959` $122.90 + UA `7416202960` $227.04 = `M801 TTL349.94`). The "first M5 wins" passenger loop dropped every ticket after the first, losing both the service line and its cost. `formatParsedData` (both `iurParser.js` and `iur-service/src/iur_parser.py`) now emits one passenger/service entry **per validating carrier** for such passengers and accumulates each into `costByPassengerType`. Three guards keep this from firing on look-alikes â€” **all three must hold**, or it falls back to the original single-ticket path:
  1. Passenger has **no M2 fare** (so Type-1/NDC ticket IURs are untouched).
  2. Passenger has **no exchange/reissue M5 row** â€” otherwise the non-exchange rows are historical originals that were exchanged away (see the over-voidation gotcha above); emitting them resurrects voided tickets.
  3. The tickets span **2+ different validating carriers**. Multiple ticket numbers under the *same* carrier are a conjunction ticket (one fare repeated across stock numbers) â€” collapse to the first row per carrier, or you **double the cost**.
  Regression-checked: across the 42 sample IURs in `iurs new/`, only the split-ticket file changed; reissue, conjunction, EMD, group, and void files are byte-identical. **Known limitation:** both tickets land in one pax-type group, so `createIUR`'s per-pax-type averaging shows each line at the *averaged* base (e.g. ~120.50) rather than the true 100/141 split â€” the grand total is correct, but per-line per-ticket fares are not. Decoupling that needs per-ticket service grouping in `createIUR`.

- **Upload-Iur.jsx `prepareIURDataForSave` is an ALLOWLIST, not a passthrough.** It builds `dataToSend` by hand-picking fields from the parsed object â€” a field can exist in `parseIURRecords`/`formatParsedData` output (and render in the upload screen's display panel via `selectedIUR.data.*`) yet still be **dropped from the `CreateIUR` payload** because it isn't copied into `dataToSend`. This is exactly how M8 `invoiceRemarks` reached the backend as `undefined` despite the parser producing them. The Python watcher (`iur_parser.py`) sends the full object, so the two upload paths can disagree on which fields arrive. **When adding any new parsed field the backend must read, add it to `dataToSend` in `prepareIURDataForSave` (~Upload-Iur.jsx:754) too** â€” don't assume the UI forwards it.

- **M8 invoice remarks (IU8REM) print on the customer invoice.** `createIUR` builds `iurInvoiceRemarks` (all M8 record `content` lines joined by `\n`) near the top and sets it as `remarks` on every IUR-created invoice (ticket/EMD/reissue rows). `invoiceDocument.ejs` renders them in the "Remarks:" block, one `<li>` per line, deduped across invoices. The render query at `document.controller.js:~1374` returns all invoice columns (no `attributes` restriction) so `remarks` flows through; the secondary list query at `document.controller.js:164` was given an explicit `"remarks"` attribute. **Caveats:** (1) M8 lines are shown verbatim â€” including `NET`/`MU` (net cost + markup) and payment lines, which exposes margin to the customer; this is per client request, invoice-only. (2) An `M801BILL/<cust>` routing line, if present, is also an M8 remark and would print â€” filter in the `iurInvoiceRemarks` builder if that becomes undesirable. (3) `costDocument.ejs` is intentionally NOT touched.

## 9b. Per-pax-type document consolidation (current behavior)

After every IUR (both new-ticket and void), `createIUR` calls two helpers defined just above it in the same file:

- `_regenerateConsolidatedInvoiceDocs({ orderId, branch, userId, autoInvoiceStatus, paxTypesFilter })`
- `_regenerateConsolidatedCostDocs({ orderId, branch, userId, paxTypesFilter })`

What they do, for each pax type the IUR touched (or all pax types if no filter is passed):

1. For each service in the order whose SPs include that pax type, run `_reconcileServiceInvoices(serviceId, activeCount, voidedCount)` (and the matching cost helper). The reconciler:
   - Voids any active invoice/cost whose `quantity` no longer matches the active SP count.
   - Creates a replacement row on the same service with the correct quantity. Per-unit price/markup/taxes are copied unchanged (taxes are per-unit by convention, so multiplying by the new quantity in the template gives the right total).
   - Returns the currently-active invoice/cost rows.
2. Group the active rows by pax type (invoice) or by `(supplier_id, pax type)` (XO).
3. Delete `document` rows whose `document_id` points at any of those active rows â€” this breaks stale doc associations so each active row ends up under exactly one (the new) document number.
4. Allocate a fresh doc number via `_allocateNextDocNumber` (same gapless scheme as before, scoped to branch prefix).
5. Insert new `document` rows, update each active invoice's `invoice_number` to the new doc, and call `generateDocumentPDF`.

End result invariant: each order has at most **one active invoice document per pax type** and **one active XO document per (supplier, pax type)**. Voided invoices/costs remain in the DB pointing at their original document numbers, so historical PDFs still resolve.

The void path of `createIUR` is split into two stages, both inside the `isVoid` branch (just before `return res.status(200)`):

1. **Always-on reconciliation** â€” calls `_reconcileServiceInvoices` and `_reconcileServiceCosts` per affected service regardless of `shouldAutoGenerateInvoice`. This is what keeps the receipt settlement listing (`customer.controller.js:getOrdersByCustomerId`) honest: the listing already filters out `status='Void'` invoices, but without this stage the original invoice would keep its pre-void quantity/total and the settlement screen would bill for tickets that are already voided.
2. **Gated doc regeneration** â€” calls the consolidated helpers only when `shouldAutoGenerateInvoice` is true. Doc PDFs are an auto-invoice-only artifact; the underlying row state must be correct regardless.

`paxTypesFilter` is built during stage 1 from the voided SPs' passenger types and reused for stage 2. The new-ticket path calls the consolidated helpers at the same point where the old per-file document block lived (now removed), passing the file's `passengerTypes` array as the filter.

**Replacement invoice starts at `Raised` with no `invoice_number`.** Two downstream paths pick it up cleanly:
- **Auto-invoice customers**: `_regenerateConsolidatedInvoiceDocs` (stage 2 above) runs immediately, bumps the replacement to `Printed` and assigns a fresh `document_number`. Settlement listing then shows it.
- **Manual customers**: the replacement appears in `invoice.controller.js:listAllOrderServiceInvoices` (which gates on `status === 'Raised' && no document`), so the operator can issue a fresh invoice document via Order Detail â†’ Options â†’ Invoice. Once printed it shows in receipt settlement.

Earlier attempts to inherit the old invoice's status (Printed) onto the replacement broke the Options â†’ Invoice dialog â€” the dialog explicitly excludes non-`Raised` invoices, so a `Printed`-but-no-doc replacement would be invisible to both flows. Don't reintroduce that inheritance without also relaxing the dialog filter.

**Read-side reconciliation in `invoice.controller.js:listAllOrderServiceInvoices`.** Legacy orders (imported before the always-on reconciler landed in `createIUR`) can be in a stuck state: SP voided but the original invoice still `Printed` with stale quantity, no Raised replacement, so the Options â†’ Invoice dialog has nothing to offer. The endpoint runs a small reconciler at the top â€” for each service in the order with voided SPs and a non-Void invoice whose quantity exceeds the active SP count, void the stale invoice and create a Raised replacement. Idempotent (quantity-match short-circuits), and only does work when something is wrong, so it's safe to leave on every read. If you're touching this code, keep the logic in sync with `_reconcileServiceInvoices` in `service.controller.js`.

This supersedes the old "single document per IUR file" behavior. If you regress this, expect the final state to fragment into one doc per file again.

## 10. Ticket voidation behavior (document rendering)

When a void IUR comes in, the backend marks matching rows in `service_passenger` with `is_voided = true` (see `createIUR` ~lines 1534â€“1620) and does **not** create new services. The parent `service`, `cost`, and `invoice` rows stay intact â€” only the `service_passenger.is_voided` flag flips, plus `updated_at` becomes the void timestamp.

Both PDF templates render voided passengers using the same time-based rule, keyed off `passenger.updated_at` vs the document's `created_at`:

| Was voided when? | Behavior on the document |
|---|---|
| **Before** the doc was created | Passenger is excluded from the line item (`.filter(p => !wasVoidedBefore...)`) AND the quantity is reduced by that count, so totals shrink accordingly. |
| **After** the doc was created | Passenger still appears (strikethrough text, red background, "VOIDED" badge), and a red "Voided Ticket Notice" banner lists them above the items table. Totals are NOT changed â€” the historical document shows what was originally billed. |

Implemented in both templates with parallel structure:
- Invoice: `power_suite_backend/views/pages/invoiceDocument.ejs` â€” helper `wasVoidedBeforeInvoice`, banner ~line 791â€“813, quantity adjust ~line 830â€“836, passenger row ~line 1441â€“1459.
- Cost/XO: `power_suite_backend/views/pages/costDocument.ejs` â€” helper `wasVoidedBeforeCost`, banner just before the items table, quantity adjust in the per-cost calc block, WHT calc in the tfoot loop, passenger row in the passenger-table block.

If you add a third document type (credit note, debit note, refund slip) that lists passengers, mirror the same `wasVoidedBefore{Type}` pattern â€” keep the rule "voided before issuance = drop, voided after = strikethrough" consistent across all templates.

To regenerate a doc with voided-after passengers dropped (e.g. customer demands a clean invoice), the operator currently voids the document and reissues â€” there's no in-place rewrite path. Keep that workflow in mind before adding edge cases.
